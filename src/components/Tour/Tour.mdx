<Section id="overview">

A guided tour: a card that walks through a list of steps, with a spotlight on each step's target. It is non-modal. The
spotlight only dims the page around the target; it does not block it, so the person can use the highlighted control, or any
other, while the card stays on screen. Nothing is made inert and page scroll is not locked.

<Canvas of={Stories.Default} story={{ inline: false, height: "26rem" }} />

### Usage

The tour keeps no record of what was seen. The app decides when to open it and stores the outcome from the callbacks.

```tsx
import { Tour } from "@lufia/design-system/components/Tour";

<Tour
  open={open}
  steps={[
    { target: '[data-tour="search"]', title: "Find anything", body: "Type a name or a number." },
    { target: searchButtonRef, title: "Narrow it down", body: "Filters stay in place.", placement: "bottom" },
    { title: "That is all", body: "Open this tour again from the help menu." },
  ]}
  labels={{
    next: "Next",
    back: "Back",
    skip: "Skip tour",
    close: "Close tour",
    finish: "Done",
    stepOf: (current, total) => `Step ${current} of ${total}`,
  }}
  onFinish={() => {
    markSeen();
    setOpen(false);
  }}
  onClose={(reason) => {
    markDismissed(reason);
    setOpen(false);
  }}
/>;
```

Strings in the snippet are plain literals. In your app they arrive through props from your copy layer. `target` is a CSS selector
(the first visible match is used) or a ref; a `data-*` attribute on the target keeps the step independent of class names.

### Steps

Each step has a `target`, a `title`, a `body` and an optional `placement` (`top`, `bottom`, `start`, `end`, or `auto`). The card
flips to the opposite side when it does not fit on the requested one, shifts to stay inside the viewport, and scrolls inside when even
that is too small. `auto` tries bottom, then top, then end, then start and takes the first side with room (the one with the
most room when none has enough). It shares its placement code with `Popover`.

### Missing or hidden targets

A step without a target, a selector that matches nothing, or a target that is hidden (`display: none`, `visibility: hidden`, or
inside something that is) is a centred card over a dimmed page. The target is looked up again on every frame, so a step whose
target appears later moves to it, and a target that goes away turns the step into a centred card.

<Canvas of={Stories.CentredCard} story={{ inline: false, height: "26rem" }} />
<Canvas of={Stories.MissingTarget} story={{ inline: false, height: "26rem" }} />

### Following the target

The spotlight and the card follow the target on scroll (of any ancestor), resize and layout changes. A target that is off
screen is scrolled into view when its step starts (smoothly, or at once under reduced motion) and again shortly after, once the
page has settled. Nothing else scrolls the page.

### Narrow screens

Below 40rem the card is a sheet docked to the bottom edge, or to the top edge when the target would be under it, and the target
is scrolled clear of the sheet.

<Canvas of={Stories.Phone390} story={{ inline: false, height: "34rem" }} />

### Inside a modal

When the target is inside an open modal, the tour is portalled into that modal so the modal's focus trap and inert page do not
lock it out, and the modal's backdrop does the dimming. Otherwise the tour is portalled to `document.body` and stays above the
page, modals, sheets and menus at `--lufia-tour-z` (default `--lufia-z-tour`, 450: above the modal layer and the sheets,
below toasts and tooltips), including a sheet or modal that opens after the tour started. An app with a fixed element above
that sets `--lufia-tour-z` on `:root`. Find the card by role (`getByRole("dialog", { name })`), not inside the page.

<Canvas of={Stories.InsideAModal} story={{ inline: false, height: "24rem" }} />

### Controlled and uncontrolled steps

Pass `stepIndex` and `onStepChange` to keep the step in the caller (for example to persist it). Without `stepIndex` the tour
keeps its own step, starting at `defaultStepIndex` each time it opens. `open` is always controlled: the tour never closes
itself, it calls `onFinish` or `onClose(reason)` and the app sets `open`.

### Steps that wait for the person

Set `mode: "do"` on a step when the person has to act on its target. The next (or finish) button is hidden, the right arrow
key does not move forward, and `labels.doHint` is shown. The tour cannot tell that the action happened: the host changes
`stepIndex` when it has. Back, skip and close stay available.

<Canvas of={Stories.DoStep} story={{ inline: false, height: "26rem" }} />

### Target status

The host says what it knows about the current step's target with `targetStatus`: `ready` (default), `seeking` (still opening
or looking, `labels.seeking` is appended to the body), `missing` (the step shows `missingBody` instead of `body`, and a `do`
step offers `labels.skipStep` in place of next; the last step still says `finish`) or `blocked` (something else is in the way,
and the body is `labels.blocked`). The tour does no detection of its own.

<Canvas of={Stories.Seeking} story={{ inline: false, height: "26rem" }} />
<Canvas of={Stories.Blocked} story={{ inline: false, height: "26rem" }} />

### Custom targets

`resolveTarget(step)` finds the target in place of the step's `target` (return `null` to fall back to it). When the element it
returns only stands in for the real target, such as the button that opens a menu holding the hidden item, `isStandIn(element,
step)` returns `true` and the step's `standInNote` is appended to the body.

<Canvas of={Stories.CustomTarget} story={{ inline: false, height: "26rem" }} />

### Typing

While a text field outside the card has focus and holds a value, a step change does not move focus to the card's heading:
that would lose the person's place. With `compactOnTyping`, on screens below 40rem the card gets `data-compact` while such a
field has focus, and its body, hint, note and step counter are hidden so the card does not cover the field: the title, the
close button and the actions stay. It grows back 300 ms after focus leaves and never while a press is in progress, so a
button does not move under a finger.

Pass `compactOnTyping={{ hideBelowHeight: 480 }}` to go further on a very short viewport: while the field has focus and the
visual viewport is shorter than that many pixels (an on-screen keyboard on a short phone) the card gets `data-typing-hidden`
and is `display: none`. A hidden card is out of the accessibility tree and the tab order (no invisible controls to tab to),
and the step is still announced through the live region. It returns when typing stops, or at once when the viewport grows
back. `true` keeps the compact behaviour only.

<Canvas of={Stories.CompactWhileTyping} story={{ inline: false, height: "34rem" }} />
<Canvas of={Stories.HiddenWhileTypingOnShortViewport} story={{ inline: false, height: "34rem" }} />

When `targetStatus` turns `ready` for the current step, the heading is focused again so the card is read once its target is
there. Focus is only moved from where it is idle (nowhere, or already on the card): a field being typed in, or a control the
person is using, keeps it.

<Canvas of={Stories.FocusAfterSeeking} story={{ inline: false, height: "26rem" }} />

### Inside a dialog

`dialogLayout` has three opt-in switches for a target inside an open modal: the package's `Modal` (either `renderAs`) or any
native `dialog`. `dock`: on a narrow screen a modal that fills the screen is resized to the viewport minus the card's height
and lifted clear of the card with a bottom margin (inline, with `!important`, and handed back when the tour leaves it or
closes), so the card sits below it, and scrolling the target into view leaves room for the modal's own `header` and `footer`.
Only the modal itself is resized. A wrapper that fills a custom dialog and sets its own height opts in with a
`data-lufia-tour-shell` attribute, as a direct child of the dialog; a header, body or footer is never resized. The header and
footer are the modal's direct children (or the shell's); a `header` or `footer` inside the content is content.
`beside`: on a wide screen the card goes beside the modal when there is room. `clipSpotlight`: the spotlight is cut off where
the modal's scroll area ends, and where its sticky header and footer cover it.

<Canvas of={Stories.DockedDialog} story={{ inline: false, height: "34rem" }} />
<Canvas of={Stories.DockedModal} story={{ inline: false, height: "34rem" }} />

### A step with no target under a modal

A step with no resolved target (none given, or `targetStatus` `seeking`, `missing` or `blocked`) is hosted in the topmost open
modal: the last native `dialog` that matches `:modal`, else the last `[aria-modal="true"]` element, else the body. On the body
the card would be inert and under the top layer of a `showModal()` dialog, so its buttons could not be seen or clicked. When
the target resolves, the card moves to the modal that holds it, as before. The `dialogLayout` switches only apply to a
resolved target.

### Leaving from the last step

The skip button is hidden on the last step, where the finish button ends the tour. A host that always offers an explicit leave
action sets `skipOnLastStep`: skip stays beside finish and calls `onClose("skip")` exactly as on earlier steps. A last step in
`do` mode has no finish button, so with `showCloseButton={false}` the skip button is shown even without the prop: the card
never has no action.

### Switches and hooks

`showCloseButton`, `closeOnEscape` and `arrowKeyNavigation` turn the package's own close button, Escape handling and arrow
keys off, one by one, for a host that owns that behaviour. Stable attributes for host CSS and tests: the overlay root has
`data-lufia-part="layer"`, the card has `data-lufia-part="card"`, `data-mode` (`read` or `do`), `data-status` (the
`targetStatus`), `data-kind` (`float`, `sheet` or `center`) `data-compact` while compact, `data-typing-hidden` while hidden for typing, and the spotlight has
`data-lufia-part="spotlight"`.

<Canvas of={Stories.SwitchesOff} story={{ inline: false, height: "26rem" }} />

### What the tour does not do

It has no routes or navigation between pages, no detection of whether the person did what a `do` step asks, and no
persistence. An app that needs those drives the tour from its own state: change `stepIndex` when the person does the thing,
and set `open` when the tour should show.

### Keyboard

| Key                | Where             | Action                                                                                      |
| ------------------ | ----------------- | ------------------------------------------------------------------------------------------- |
| Right / Left arrow | Focus on the card | Next / previous step (reversed in right-to-left text); an arrow key never finishes the tour |
| Escape             | Card or no focus  | Calls `onClose("escape")`                                                                   |
| Tab / Shift+Tab    | Card              | Moves between the card's buttons; focus is not trapped                                      |
| Enter / Space      | A button          | Activates it                                                                                |

The right arrow does not move forward on a `do` step. Escape and the arrow keys act only while focus is on the card (Escape also when nothing in the page has focus), never while
focus is in a field of the page, so they do not take keys from the app. The tour registers on the shared overlay stack, so a
menu or dialog opened from the page above the tour closes first and the tour on the next Escape.

### Accessibility

- The card is `role="dialog"` with `aria-modal="false"`, named by the step title and described by its body. The page behind
  stays in the accessibility tree and operable.
- Each step moves focus to the card's heading (without scrolling the page) so a screen reader reads the new step. A hidden
  polite status region announces the counter from `labels.stepOf` when the step changes.
- Closing from the card hands focus back to the element that had it when the tour opened, when that element is still in the page.
- The spotlight and the dimming are decoration (`aria-hidden`) and never the only signal: the card says what the step is about.
  In forced-colors mode the spotlight is a `Highlight` border and the card border is `CanvasText`.
- The card is portalled to the end of the body, so the browser's Tab order leaves it at the end of the page; the arrow keys and
  the buttons are the way through the steps.
- A sheet, menu or dialog opened after the tour started sits below the card (`--lufia-tour-z`). The package's inert page
  skips the tour layer, so the card stays operable by pointer. The overlay's focus trap still owns Tab and Shift+Tab while
  focus is inside the overlay, so the card is not in the keyboard path then; once focus is on the card (a press on one of its
  buttons) Tab follows the browser's order instead of being pulled back. A step whose target is outside such an overlay stays on
  `document.body`; a step with no target is hosted in the topmost open modal, as above.
- The card and its content fade in; the spotlight glides between targets. Under reduced motion both appear without motion and
  scrolling is not smooth.

<Section id="guidelines">

### When to use

- Introducing a screen's main controls once, the first time a person visits it.
- A short, optional walkthrough that can be reopened from a help menu.

### When not to use

- Instructions the person needs to complete a task: put them next to the control, in help text.
- A choice or a question: use `Modal` or `ConfirmDialog`.
- Anchored content without steps: use `Popover`.
- Anything long. Keep a tour to about five steps and let the person skip it.

### Content guidelines

Titles say what the control is for ("Find anything"). Bodies are one or two short sentences. Always offer `skip` and `close`
through `labels`, and never start a tour the person did not ask for more than once.

</Section>
