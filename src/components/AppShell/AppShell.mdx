<Section id="overview">

The frame of an application. On wide screens a sidebar with groups that open and close and that can shrink to a rail. On
phones a sticky top bar, a floating bar within thumb reach, and a navigation sheet that rises from the bottom. The
navigation is data, so both layouts always agree.

### Usage

```tsx
import { AppShell } from "@lufia/design-system/components/AppShell";

<AppShell
  groups={[
    {
      key: "workspace",
      label: "Workspace",
      items: [
        { key: "home", label: "Overview", href: "/", icon: <HomeIcon />, exact: true },
        { key: "inbox", label: "Inbox", href: "/inbox", icon: <InboxIcon />, badge: 3 },
      ],
    },
    {
      key: "insights",
      label: "Insights",
      collapsible: true,
      items: [{ key: "reports", label: "Reports", href: "/insights/reports" }],
    },
  ]}
  currentPath={pathname}
  labels={{
    skipToContent: "Skip to content",
    navigation: "Main navigation",
    menu: "Menu",
    floatBar: "Quick navigation",
    collapseSidebar: "Collapse sidebar",
    expandSidebar: "Expand sidebar",
  }}
  brand={({ collapsed }) => <Logo compact={collapsed} />}
  footer={<AccountLinks />}
  search={{ label: "Search…", shortcut: "Ctrl K", onSelect: openPalette }}
  primaryAction={{ label: "New item", icon: <PlusIcon />, onSelect: createItem }}
>
  <PageContent />
</AppShell>;
```

Strings in the snippet are plain literals. In your app they arrive through props from your copy layer. Links render through the
`linkComponent` of `LufiaProvider`, so a router's client-side navigation works; pass `currentPath` from its hook.

### Parts

The shell is built from parts that are exported, so an app with another arrangement composes its own.

| Part                                                                | What it is                                                                     |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `AppShell`                                                          | The whole frame, wired to `groups`                                             |
| `Sidebar`, `SidebarGroup`, `SidebarItem`                            | The desktop sidebar and what goes in it                                        |
| `ShellNavigation`                                                   | Renders `groups` data as groups and items, for the sidebar and the sheet alike |
| `MobileFloatBar`, `MobileFloatBarButton`, `MobileFloatBarSeparator` | The floating bar and its controls                                              |
| `RouteProgress`                                                     | The thin top progress bar for a loading navigation                             |
| `ShellFooter`, `ShellFooterItem`                                    | The icon-and-label actions at the foot of the sidebar and of the sheet         |
| `NavSheet`                                                          | The modal bottom sheet with swipe-to-dismiss                                   |
| `serializeShellState`, `parseShellState`                            | The cookie value that remembers the rail and the open groups (server-safe)     |
| `findActiveNavKey`                                                  | The matcher behind `currentPath`                                               |

#### Marking the current page

`currentPath` makes the item whose `href` equals it, or contains it, current. The most specific item wins, so
`/settings/billing` is never current together with `/settings`; `exact: true` (or `match: "exact"`) limits an item to its
own path. Query strings and hashes are ignored unless an item asks for them with `match`:

| `match`               | The item is current when                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------------------ |
| `"prefix"` (default)  | the path equals its `href` or sits below it                                                            |
| `"exact"`             | the path equals its `href`                                                                             |
| `"query"`             | the path equals its `href` and every query parameter of its `href` has the same value in `currentPath` |
| `(currentPath, item)` | the function returns true; it receives `currentPath` as you passed it, query included                  |

For `"query"` and for functions, pass `currentPath` with its query string (`pathname + "?" + search`); the other items
keep ignoring it. When several items match, a function beats `"query"`, `"query"` beats a path, and between paths the
longest wins, so one item is current at a time. Pass `isActive` on the shell instead when your routes do not map to paths
at all.

A click on a link makes it look current at once and closes the sheet; `aria-current` stays on the real page until
`currentPath` changes.

#### Groups, the rail and slots

- A group with `collapsible` and a `label` is a disclosure button over its items. Groups marked `defaultOpen`, and the one
  holding the current page, start open; arriving on a page inside a closed group opens it. Own the state with `openGroups`
  and `onOpenGroupsChange` to persist it; the package stores nothing (see "Remembering the rail and the groups").
- The rail (`collapsed`, `defaultCollapsed`, `onCollapsedChange`) shows icons only. Names stay in the DOM and a tooltip
  shows the label on mouse hover and on keyboard focus, never on touch (see "Rail tooltips"). A rail shows the items of
  collapsible groups too, because a closed group would hide icons. `fixedSidebar` removes the rail button.
- `brand` and `footer` take a node or a function that receives `{ collapsed }`, so a logo can shrink to its mark.
  `topBarEnd` fills the right of the phone top bar.

#### Sub-items

An item can hold one level of `items`: sections under one page, such as the parts of a settings or back-office area chosen
by a query string. They are listed under the item, indented on a guide line, while the item or one of them is current
(`expanded: true` lists them always), and they open and close with `Collapse`. Deeper `items` are ignored.

```tsx
{
  key: "admin",
  label: "Administration",
  href: "/admin",
  icon: <GearIcon />,
  items: [
    { key: "people", label: "People", href: "/admin?section=people", match: "query" },
    { key: "roles", label: "Roles", href: "/admin?section=roles", match: "query" },
  ],
}
```

- **Current state.** The current sub-item has `aria-current="page"`; the item that holds it is drawn as the open branch
  (`data-branch`) and has no `aria-current`, so exactly one link is the page. A collapsible group that holds the current
  sub-item opens like it does for its own items.
- **Keyboard.** Sub-items are ordinary links after their item in the tab order. Folded sub-items are `inert`, so Tab never
  lands on something hidden.
- **The rail** hides the sub-items rather than opening a flyout: a flyout would be a second menu pattern to learn and to
  reach by keyboard. The item's icon links to its own `href`, its tooltip names it, and while one of its sub-items is
  current it takes the active look and `aria-current="true"` (current within the set, not the page itself). So give an
  item with sub-items an `href`: its overview or its first section. In the phone sheet the sub-items show as in the open
  sidebar.

#### Nav item extras

A `ShellNavItem` takes more than a label and an `href`:

- `count` is a number after the label: hidden at 0, shown as `99+` above 99, in the tone of `countTone` (`neutral`,
  `success`, `warning` or `danger`). In the rail it sits on the corner of the icon. Pair it with `ariaLabel` ("Inbox, 7 unread")
  so the tone's meaning is also in words. `badge` stays for a word such as "New", with `badgeTone` (default `warning`, or `neutral`, `success`, `danger`); in
  the rail a word badge steps aside for a count on the same item.
- `className` and `data` (an object of `data-*` attributes) go on the link or button itself: styling hooks, analytics,
  guided-tour anchors, test ids.

#### Rail tooltips

In the rail every control that lost its label (items, the search entry, the rail button, footer items) shows a tooltip.
It appears after a short hover delay and at once on keyboard focus (`:focus-visible`), never on touch, where a tap would
leave it stuck. Escape, leaving, blur and scrolling dismiss it, and it stays while the pointer is over it (WCAG 1.4.13). It
fades with `--lufia-motion-duration-fast` and nothing else moves; reduced motion removes the fade. It is drawn in
`document.body`, so a scrolling navigation never clips it, and it is `aria-hidden`: each control already carries the same
text as its accessible name, so nothing is announced twice.

#### Footer

`ShellFooter` and `ShellFooterItem` build the foot of the sidebar and of the sheet: one column in the sidebar, icons only in
the rail, two columns in the sheet. An item is a link through the configured `linkComponent` (`href`), a plain external
anchor (`href` with `external`, and `target="_blank"` adds `rel="noopener noreferrer"`), or a button. `type="submit"` suits a
sign-out form, `pressed` makes a toggle (a theme switch), `active` marks the current page, `count` adds a capped count and
`tone="warning"` colours a caution. `pending` dims the item, sets `aria-busy`, ignores further clicks and keeps focus where it
is, which is why it does not use `disabled`.

```tsx
<AppShell
  footer={
    <ShellFooter aria-label="Account and help">
      <ShellFooterItem label="Settings" href="/settings" icon={<GearIcon />} active={path === "/settings"} />
      <ShellFooterItem
        label="Help"
        href="/help"
        icon={<HelpIcon />}
        count={unreadReplies}
        countTone="danger"
      />
      <form action={signOut}>
        <ShellFooterItem label="Sign out" type="submit" icon={<ExitIcon />} pending={signingOut} />
      </form>
    </ShellFooter>
  }
/>
```

A link in the footer of the phone sheet closes the sheet like any other link.

#### The page area and where banners sit

The shell owns the one `<main>`. Three places sit around it, and the choice decides what stays put:

| Slot                  | Where it is                                         | Use for                                                                                                  |
| --------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `topBar`, `statusRow` | Beside the sidebar, above `<main>`, a sibling of it | Context that stays put at every width: a unit picker, a sync state. Never remounted with the page.       |
| `mainStart`           | First child inside `<main>`, before `children`      | Banners that belong to the page area and scroll with it: a trial notice, an install hint, a page notice. |
| `children`            | Inside `<main>`                                     | The page.                                                                                                |

`mainProps` sets attributes on `<main>` (`id`, `className`, `data-*`, `tabIndex`, ARIA); the skip link follows its `id`.
`mainKey` works like React's `key`: when it changes (a workspace or scope switch) the `<main>`, its banners and the page
inside remount and drop their state. Leave it out for ordinary page changes.

#### Context and the phone sheet

`context` is the slot for where the person is working: a workspace, company or account card with its switcher. It sits
between the brand and the search in the sidebar and above the navigation in the sheet. A function slot receives
`AppShellSlotState`: `surface` (`"sidebar"`, `"sheet"` or `"topBar"`), `collapsed` (only ever true in the sidebar rail),
`closeSheet()` and `openSheet()`. So one switcher can open as a dropdown in the sidebar, inline in the sheet, and close the
sheet when it navigates. `brand`, `footer`, `context` and `searchTrigger` all get this state, and each is rendered once per
surface: do not give its parts a fixed `id`.

The phone sheet can be controlled: `menuOpen` and `onMenuOpenChange` let a control of your own open it (a workspace chip in
the top bar), and `hideSheetNavigation` leaves only `context` and the footer in it while a switcher has taken over.
A followed link inside the sheet, footer and slots included, closes it.

#### Route motion, progress and the pending page

Give the shell the current page's `routeKey` (the pathname, not the query) and it takes care of the motion around a
navigation; every piece is optional and none remounts the page.

| Prop                   | What it does                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `routeKey`             | When it changes, the arriving page fades in and rises (`RouteTransition`). Not on first load, not for a search-param change. Banners in `mainStart` and fixed elements are left alone. Adds one element around `children`.                                                                                                                                                         |
| `routePending`         | A navigation has started: a thin bar at the top of the window, shown only if the wait outlasts 150 ms. Without `routePending`, a plain click on a same-origin link to another path starts it by itself (a link that only changes the query or hash does not); `routeKey` changing, the address changing, or 10 seconds finish it, so a cancelled navigation never leaves it stuck. |
| `mainPending`          | A skeleton in `<main>` in place of the page. The page stays mounted but `hidden` (a wrapper the shell always renders, so showing the skeleton never remounts it, and hidden content leaves the tab order); focus that was inside it moves to `<main>`; `mainStart` stays; `<main>` is `aria-busy` (your own `aria-busy` is kept). After a skeleton the page only fades.            |
| `routeTrackLinks`      | Link clicks start the bar alongside `routePending`: the bar shows while either is in progress. Default `true` without `routePending` and `false` with it. Set it `true` to drive query-string navigations (which link tracking ignores) through `routePending` and keep tracking link clicks. The 10-second safety timeout still ends any run.                                     |
| `routeTransitionProps` | A `className` and `data-*` attributes for the region that plays the route motion, so your own CSS can stagger the arriving page's sections off the `data-route-enter` its children get. Animate `transform` and `opacity` only and turn it off under `prefers-reduced-motion` (the shell sets no marker then anyway).                                                              |
| `routeProgress`        | `false` turns the bar off while keeping the rest.                                                                                                                                                                                                                                                                                                                                  |

Timing is yours: when to show `mainPending` (most apps wait a few hundred milliseconds, so fast navigations never show a
skeleton), when a wait is long enough to offer a retry, and what the skeleton looks like. `RouteProgress` is also exported
for an app that draws the bar itself.

#### Floating bar fade

`floatScrim` (default off) draws a gradient from the canvas colour behind the floating bar on phones, so content scrolling
under the bar fades out instead of ending in a hard edge. Nothing is drawn unless you ask.

#### Primary action details

`primaryAction.onIntent` fires when the pointer enters the control or it takes focus, on the floating bar and in
`ShellPrimaryActionSlot`: warm the destination there. `desktopPrimaryFallback={false}` keeps the shell's default action out
of the wide-screen slot until a page registers its own (the phone bar still shows the default), so a hard load never
flashes an action the page is about to replace. The default is marked `data-fallback` until a page takes over, for CSS.

#### A long navigation scrolls itself

When the list is taller than the window, both the sidebar and the sheet fade the edge that hides more items
(`data-more` on the scroller) and bring the current page into view, once for each page and never on a group toggle.

#### What stays in the app

The shell frames the product; these remain the app's own, composed through slots:

- the search or command palette itself (use `CommandPalette`), its data and any AI-assisted query;
- the workspace and unit pickers, mounted in `context`, `topBar` or `mainStart`;
- route prefetching (`onIntent` is the hook), skeleton shapes per page, and long-wait copy;
- where the theme, the account and the session live (the footer's items call your functions).

#### Remembering the rail and the groups

The package stores nothing. Hold the choice in a cookie, not `localStorage`: a server can read a cookie before it renders, so
the first paint is already the right one and nothing flashes open and then shuts. `serializeShellState` writes a cookie-safe
value and `parseShellState` reads it back on the server or in the browser; hand the result to `defaultCollapsed` and
`defaultOpenGroups`, and save on the two change hooks.

Both also come from `@lufia/design-system/app-shell-state`, a module with no React and no `"use client"`, so a React Server
Component, a route handler or middleware can import them without pulling the shell's client code into the server layer.

```tsx
// Server component (any framework that exposes the request cookie)
import { parseShellState } from "@lufia/design-system/app-shell-state";
const saved = parseShellState(cookieStore.get("shell")?.value);

<AppShellClient initial={saved} />;

// Client component: keep the latest choices and write them with one small function
("use client");
function AppShellClient({ initial }: { initial: ShellState }) {
  const state = useRef(initial);
  const save = (patch: Partial<ShellState>) => {
    state.current = { ...state.current, ...patch };
    document.cookie = `shell=${serializeShellState(state.current)}; path=/; max-age=31536000; samesite=lax`;
  };
  return (
    <AppShell
      defaultCollapsed={initial.collapsed}
      defaultOpenGroups={initial.openGroups}
      onCollapsedChange={(collapsed) => save({ collapsed })}
      onOpenGroupsChange={(openGroups) => save({ openGroups })}
      /* groups, labels, children... */
    />
  );
}
```

`openGroups` stays `undefined` until the person opens or closes a group, so the defaults (`defaultOpen`, the group of the
current page) apply until then. The cookie only supplies initial state: the shell stays uncontrolled, and arriving on a page
inside a closed group still opens it. Pass `collapsed` and `openGroups` instead if your app owns the state.

### Phones

Below `60rem` (the `--lufia-breakpoint-medium` token) the sidebar gives way to the top bar, the floating bar and the sheet.
The page gets bottom padding and `scroll-padding` so nothing hides under the bar.

#### Floating bar

<Canvas of={FloatBarStories.Default} />

A pill fixed above the safe area, translucent where the browser can blur (solid under `prefers-reduced-transparency`, and
where `backdrop-filter` is missing). It holds a search entry, the page's one main action and the menu button. The search
entry gives way first when the bar is crowded; the main action then ends in an ellipsis, and below 22.5rem it shows only
its icon. All keep their accessible names.

The bar follows the visual viewport (`followViewport`, default on): where the on-screen keyboard or a browser toolbar
covers the bottom of the page (iOS Safari keeps fixed elements on the layout viewport, behind them), it moves up above it,
read from `window.visualViewport` once per frame and written as `--lufia-float-bar-viewport-offset`, with
`data-viewport-lifted` while lifted. It moves with `transform` and does not ease, so it never trails the keyboard. It does
nothing while the page is pinch-zoomed and where `visualViewport` does not exist.

#### Navigation sheet

<Canvas of={SheetStories.Default} />

`NavSheet` is a modal dialog, mounted in `document.body` (set `container` to change that) so the rest of the page can be
made inert. Pass `swipeToDismiss={false}` to turn the gesture off, for the grabber, the header and the body alike.

#### Theming the portalled sheet

The sheet is portalled to `document.body`, outside the shell. A palette an app scopes to its own wrapper (a class or a
`data-*` attribute that redefines the `--lufia-*` tokens, such as a dark scope) therefore does not reach it, and the sheet
would open in the page's default palette. Three ways to scope it:

- **Lufia theme attributes on a wrapper.** When an ancestor of the shell (not `<html>`) sets `data-lufia-theme` or
  `data-lufia-mode`, the sheet copies them onto its layer each time it opens.
- **`sheetProps`.** A `className` and `data-*` attributes for the sheet's outermost layer (the fixed root of the backdrop
  and the panel, or the `<dialog>`): repeat the class or attribute that scopes your palette,
  `sheetProps={{ className: "app-dark" }}`.
- **`sheetProps.container`.** Mount the sheet inside your scoped wrapper instead of `document.body`.

Stable hooks for styling: `data-lufia-part="nav-sheet-layer"` (the fixed root), `"nav-sheet-backdrop"` and `"nav-sheet"`
(the panel).

### Slots

| Prop                                            | What it does                                                                                                                                           |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `topBar`, `statusRow`                           | Bars beside the sidebar, above the page, at every width (a unit picker; sync state). The page stays a direct child of the shell when both are omitted. |
| `navigationPending`                             | A skeleton shown in place of the navigation (sidebar and sheet) while a route loads; `aria-busy` meanwhile.                                            |
| `searchTrigger`                                 | Replaces the sidebar search entry. `search` still drives the floating bar entry and takes `shortcut` (a `kbd`), `keyShortcuts`, `opensDialog`.         |
| `primaryAction`                                 | The default main action. A page replaces it with `useShellPrimaryAction`, and `ShellPrimaryActionSlot` shows it on wide screens.                       |
| `mainProps`, `mainKey`, `mainStart`             | Attributes of `<main>`, a remount key, and banners inside it (see "The page area and where banners sit").                                              |
| `menuData`, `search.data`, `primaryAction.data` | `data-*` attributes on the floating bar controls (analytics, guided tours).                                                                            |
| `sheetAs="dialog"`                              | The phone navigation sheet as a native `<dialog>` in the top layer (see `Modal` `renderAs`).                                                           |
| `sheetProps`                                    | A `className`, `data-*` attributes and a `container` for the phone sheet, to carry a scoped palette to it (see "Theming the portalled sheet").         |

Nav items take an `ariaLabel` when the accessible name should add to the label ("Inbox, 3 unread"). A group without a
`label` is a plain run of items; a group with a `label` and no `collapsible` has a static heading. A page registers its
action with `useShellPrimaryAction`: the first registration of a page keeps its place when it updates, and a newly
mounted page takes over from the older one.

### Data attributes

`data-collapsed` on the shell and the sidebar, `data-active` on the item that looks current, `data-branch` on an item whose
sub-item is current, `data-sub-items` on the folding list of sub-items, `data-open` on an open group,
`data-viewport-lifted` on the floating bar while it is above the keyboard,
`data-state="open|closed"` on the sheet and `data-dragging` while it is dragged. Use them to style slot content.

### Keyboard and accessibility

| Key             | Where              | Action                                                         |
| --------------- | ------------------ | -------------------------------------------------------------- |
| Tab / Shift+Tab | Everywhere         | Moves through the skip link, the sidebar and the page in order |
| Enter           | Link               | Follows it                                                     |
| Enter / Space   | Button, group head | Activates it; a group head toggles `aria-expanded`             |
| Escape          | Sheet              | Closes it; focus returns to the menu button                    |
| Tab / Shift+Tab | Sheet              | Cycle inside the sheet; the page behind is inert               |

- **Landmarks.** The page is wrapped in the only `<main>`; do not render another. A skip link to it is the first tab stop.
  The sidebar and the sheet each hold a `<nav>` named by `labels.navigation`. The sidebar is hidden (`display: none`) below
  the breakpoint, so a phone never sees two.
- **Current page.** `aria-current="page"` on exactly one link. While a group is closed, its button shows the active style
  to point at the page inside it. In the rail, an item whose hidden sub-item is current has `aria-current="true"`.
- **Swipe is an enhancement.** Dragging the grabber or the header down dismisses the sheet. The body keeps native scrolling:
  a drag that starts in the body counts only when the body is scrolled to the top and moves down, and then it follows the
  finger (and cancels the browser's pull to refresh) as on a native bottom sheet. A list inside the body that scrolls on its
  own is respected: the drag starts only when it and the body are both at the top. Any other move scrolls, nothing is cancelled
  until the direction is known (so a row that scrolls sideways still does), and a sideways move is left alone. The click the
  lifted finger would send to a link under it is swallowed for a moment, never longer than the next touch. Escape and the close button always
  work. A short drag springs back; a past-threshold release or a quick flick dismisses. The offset follows the finger even
  under reduced motion, because it is direct manipulation.
- **Focus.** The sheet traps focus, lands it on the dialog itself (nothing is chosen for the person, and no keyboard
  pops up on touch), and gives it back to the opener. Body scroll is locked.
- **The floating bar is a labelled group**, not an ARIA toolbar: a toolbar promises arrow-key movement and every control
  here is a plain tab stop.
- **Targets** are at least 2.75rem (44px). Focus is a 2px ring. The active item has a bar on its inline-start edge besides the
  colour, and a `Highlight` border in forced-colors mode.
- **Motion.** The sheet rises and the backdrop fades with the `--lufia-motion-*` tokens; exits are shorter than entrances.
  Groups use `Collapse`. Under `prefers-reduced-motion` the sheet appears and disappears at once. The sidebar width changes
  without animation, on purpose: animating it would animate layout.
- **Right to left.** Logical properties throughout; chevrons mirror.

<Section id="guidelines">

### When to use

- A signed-in application with a handful of top-level areas, on both phones and desktops.

### When not to use

- A marketing site (use a header), or navigation that is only a few peer views of one page (use `PeerNav`).

### Content guidelines

Item labels are one or two words. Put the rarely used areas in a collapsible group and the one thing the page is for in
`primaryAction`. The search label is a verb phrase ("Search…").
