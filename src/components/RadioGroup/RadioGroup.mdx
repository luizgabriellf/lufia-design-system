One choice from a short, visible list. Each option has a label and may have a description. The group has a roving tab stop
and arrow-key navigation.

### Usage

```tsx
import { RadioGroup } from "@lufia/design-system/components/RadioGroup";

<RadioGroup
  label="Payment method"
  name="payment"
  value={method}
  onValueChange={setMethod}
  options={[
    { value: "card", label: "Card", description: "Charged today." },
    { value: "transfer", label: "Bank transfer" },
  ]}
  error={errors.payment}
/>;
```

Strings in the snippet are plain literals. In your app they arrive through props from whatever copy or i18n layer you use.
With `name`, the chosen value is submitted with the form.

### Naming the group without a visible label

Give exactly one of `label` (visible legend), `aria-label` (a string) or `aria-labelledby` (the id of an element the host
already shows, such as a card heading). The types reject zero or several. With `aria-label` or `aria-labelledby` there is no
legend, so no required asterisk and no hidden "required" text: a required group is announced through `aria-required` only,
and the host's own heading should carry any visible mark.

```tsx
<h2 id="pay-heading">How would you like to pay?</h2>
<RadioGroup aria-labelledby="pay-heading" name="payment" options={options} required />
```

### Card variant

`variant="card"` draws each option as a bordered, selectable row. An option can carry `meta` (inline end: a price, a badge) and `content` (under the description). Both are read as part of the option's description and live inside the radio button, so they must be phrasing content only (text, `span`, `strong`, an icon): no lists, no block elements, nothing interactive. The default stays plain rows.

```tsx
<RadioGroup
  label="Plan"
  variant="card"
  options={[
    {
      value: "basic",
      label: "Basic",
      description: "For one site.",
      meta: "9 / month",
      content: (
        <>
          Two seats, <strong>e-mail</strong> support.
        </>
      ),
    },
  ]}
/>
```

### Form events

When the user chooses an option (a click or an arrow key), a bubbling `input` Event and then a bubbling `change` Event are dispatched from the hidden input (from the group itself when there is no `name`), after the new value is in the DOM. A native listener on the `<form>` (`form.addEventListener("change", …)`) or a React `onInput` can tell that the user edited it, as with native radios. A React `onChange` on the form does not fire: React ignores hidden inputs for `onChange`, so use `onInput` there. Nothing is dispatched for a `value` that the parent sets, for a form reset, or for choosing what is already chosen. The event waits for the commit that shows the new value, so a controlled parent may accept it later (a transition works too). One edge: if the parent refuses the choice and keeps showing the old value, then later sets that same value, that one change is announced.

A form reset restores the `defaultValue` of the latest render, as native fields do, including when a form action has just changed it.

### Accessibility

Follows the WAI-ARIA APG [Radio Group](https://www.w3.org/WAI/ARIA/apg/patterns/radio/) pattern.

| Key / action       | Behaviour                                                                         |
| ------------------ | --------------------------------------------------------------------------------- |
| Tab / Shift+Tab    | Enters the group at the chosen option (the first enabled one if none); leaves it. |
| Down / Right arrow | Moves to the next option and chooses it. Wraps. Skips disabled options.           |
| Up / Left arrow    | Moves to the previous option and chooses it. Wraps.                               |
| Space              | Chooses the focused option (a click).                                             |

- In right-to-left layouts Left and Right swap.
- `role="radiogroup"` named by the label (plus the hidden required text when `required`), or by `aria-label` / `aria-labelledby`; each option is `role="radio"` with `aria-checked`, named by its label and
  described by its description.
- Querying (tests and tooling): `getByRole("radiogroup", { name })` finds the group; with a visible label and `required` the name ends with the hidden suffix, so match with a regex such as `/^Payment/`. `getByRole("radio", { name: "Card" })` finds an option and its state is `aria-checked`. An empty required group has `aria-required="true"`; a refused submit focuses the first enabled radio (or the chosen one) and describes the group with the message.
- A required group blocks form submission until an option is chosen, with the browser's own message: an invisible, unsubmitted input mirrors the value for that. A form `reset` returns the group to `defaultValue`.
- The card variant changes the look only: the same roving focus, arrow keys and `radio` semantics. `meta` and `content` join the option's `aria-describedby`.
- Required adds an asterisk, the text `required` for screen readers (the `required` label of `LufiaProvider`, or `requiredLabel`), and `aria-required`.
- The error is in the group's description, with `role="alert"` and `aria-invalid`.

<Section id="guidelines">

### When to use

- Two to six mutually exclusive options, where seeing them all helps the decision.

### When not to use

- Seven or more options: use `Select` or `Combobox`.
- On/off: use `Switch` or `Checkbox`.
- A compact two-or-three-way view switch: use `SegmentedToggle`.

### Content guidelines

The group label is the question or the noun ("Payment method"). Options are parallel, short and sentence case. Describe the
consequence in the description, not the label. Pre-select the safe default when there is one; otherwise leave nothing chosen
and require a choice.
